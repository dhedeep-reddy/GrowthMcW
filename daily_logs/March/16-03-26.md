# CUDA Kernel Profiling Study Report

## Overview

Today’s work focused on understanding **GPU kernel profiling in CUDA** using **NVIDIA Nsight Compute**. The goal was to analyze the performance characteristics of CUDA kernels, identify bottlenecks, and understand how GPU hardware resources such as streaming multiprocessors (SMs), memory subsystems, and warp schedulers behave during kernel execution.

The kernel used for profiling was a **parallel reduction kernel (`reduceSum`)**, which computes the sum of an array using shared memory and thread synchronization. Profiling was conducted using both the **command-line interface (`ncu`) and the graphical user interface of NVIDIA Nsight Compute**.

---

## Tools Used

The primary tool used for profiling was **NVIDIA Nsight Compute**, which provides detailed kernel-level performance analysis.

Commands used during profiling:

* `sudo ncu ./VectorSum`
* `sudo ncu --section MemoryWorkloadAnalysis ./VectorSum`
* `sudo ncu --section ComputeWorkloadAnalysis ./VectorSum`
* `sudo ncu --section SchedulerStats ./VectorSum`
* `sudo ncu -o reduction_profile ./VectorSum`

The generated report file (`.ncu-rep`) was then opened in the Nsight Compute GUI to visually analyze performance metrics.

---

## Kernel Description

The CUDA kernel used for profiling performs **parallel reduction using shared memory**. Each thread block loads a portion of the input array into shared memory, performs pairwise summation, and writes a partial result.

Execution configuration used during profiling:

* Grid size: **4096 blocks**
* Block size: **256 threads per block**
* Total threads executed: **1,048,576**

This configuration ensured that the GPU was sufficiently utilized for meaningful profiling analysis.

---

## Speed of Light Throughput Analysis

The Speed of Light section provides an overview of how much of the GPU’s theoretical performance capacity was utilized.

Observed results:

* Compute Throughput: **~87%**
* Memory Throughput: **~87%**
* DRAM Throughput: **~28%**
* L1/TEX Cache Throughput: **~90%**
* Kernel Duration: **~51 microseconds**

Interpretation:

These values indicate that the kernel utilized a large portion of the available compute and memory resources. Nsight Compute reported that the workload was using **greater than 80% of the available GPU compute or memory performance**, suggesting efficient utilization.

---

## Launch Statistics Analysis

Launch configuration determines how threads are distributed across the GPU.

Important values observed:

* Grid Size: **4096**
* Block Size: **256**
* Registers per Thread: **16**
* Shared Memory per Block: **~1 KB**
* Number of SMs on device: **26**
* Waves per SM: **~26**

Explanation:

Since the GPU contains 26 streaming multiprocessors, blocks are distributed across them in waves. With 4096 blocks, each SM processes multiple waves of blocks, ensuring that work is continuously available for execution.

---

## Occupancy Analysis

Occupancy measures how effectively the GPU’s hardware resources are utilized.

Observed metrics:

* Theoretical Occupancy: **100%**
* Achieved Occupancy: **~84.5%**
* Active Warps per SM: **~40**
* Maximum possible warps per SM: **48**

Interpretation:

Achieving approximately 84% occupancy indicates that most of the GPU’s warp execution capacity is being used. Occupancy in the range of **60–90% is generally considered optimal**, so this result reflects efficient kernel configuration.

---

## Memory Workload Analysis

Memory workload profiling helps determine whether the kernel is limited by memory bandwidth.

Key results:

* Memory Throughput: **82.59 GB/s**
* Maximum Bandwidth Utilization: **87.32%**
* Memory Pipes Busy: **87.32%**
* Memory Busy: **47.24%**
* L1 Cache Hit Rate: **0.69%**
* L2 Cache Hit Rate: **4.20%**

Interpretation:

The kernel makes streaming memory accesses where each value is typically read once. Therefore, cache hit rates are expected to be low. However, the memory throughput and pipeline utilization are high, indicating that the kernel is efficiently utilizing available memory bandwidth.

These results strongly suggest that the kernel is **memory-bound**, meaning performance is limited by memory access speed rather than arithmetic computation.

---

## Compute Workload Analysis

Compute workload profiling evaluates how efficiently the GPU’s execution pipelines are used.

Observed results:

* Executed IPC (Instructions per Cycle): **~1.7**
* Issue Slots Busy: **~40.7%**
* SM Busy: **~43%**

Interpretation:

The GPU’s compute pipelines are moderately utilized. Reduction kernels perform relatively few arithmetic operations compared to memory accesses, so compute utilization is naturally lower than memory utilization.

This further confirms that the kernel’s performance is primarily limited by memory bandwidth.

---

## Scheduler Statistics Analysis

Scheduler statistics reveal how efficiently warps are issued to execution pipelines.

Key results:

* Active Warps per Scheduler: **~10.1**
* Eligible Warps per Scheduler: **~0.71**
* Issued Warp per Scheduler: **~0.42**
* Cycles with No Eligible Warp: **~58%**

Interpretation:

Although multiple warps are active, many are not eligible to execute in each cycle. This occurs due to factors such as:

* memory latency
* synchronization barriers (`__syncthreads`)
* data dependencies between instructions

As a result, the scheduler sometimes has no warp ready to issue instructions, leaving execution units temporarily idle.

---

## GUI Profiling Analysis

After generating a profiling report, the results were examined in the Nsight Compute GUI. The GUI provides graphical visualizations of:

* GPU Speed-of-Light utilization
* kernel launch configuration
* occupancy metrics
* memory workload distribution
* hardware activity timelines

These visual representations make it easier to identify performance bottlenecks and understand the relationship between compute utilization, memory bandwidth, and warp scheduling behavior.

---

## Key Findings

From the profiling analysis, the following conclusions were drawn:

1. The kernel achieved **high occupancy (~84%)**, indicating efficient thread scheduling.
2. Memory throughput was very high, utilizing **over 80% of available bandwidth**.
3. Compute pipelines were moderately utilized because the reduction algorithm performs limited arithmetic operations.
4. Scheduler statistics revealed periods where no warp was ready to execute due to memory latency and synchronization barriers.
5. The kernel is **primarily memory-bound**, meaning further performance improvements would require reducing memory traffic or improving data reuse.

---

## Conclusion

The profiling session demonstrated how to systematically analyze CUDA kernel performance using NVIDIA Nsight Compute. By examining multiple profiling sections—Speed of Light throughput, Launch Statistics, Occupancy, Memory Workload Analysis, Compute Workload Analysis, and Scheduler Statistics—it was possible to understand how GPU resources were utilized during execution.

The analysis confirmed that the parallel reduction kernel efficiently utilized the GPU but was primarily constrained by memory bandwidth and synchronization overhead. This insight provides a foundation for future optimization techniques such as warp-level reductions, loop unrolling, and improved shared memory utilization.

Overall, this exercise provided a comprehensive understanding of CUDA kernel profiling and the interpretation of key GPU performance metrics.
