## CUDA Matrix Multiplication & Reduction Optimization Report

### Objective

The objective of this study was to analyze, profile, and optimize GPU-based matrix multiplication and reduction using CUDA. Multiple optimization techniques were applied incrementally, and their performance impact was evaluated using Nsight Compute to understand bottlenecks and hardware behavior.

---

### System Setup

* GPU: NVIDIA GPU (Compute Capability 12.0)
* Profiler: Nsight Compute (ncu)
* Matrix Size: 1024 × 1024
* Tile Sizes Tested: 16×16, 32×32
* CPU Baseline: Tiled matrix multiplication (BLOCK = 16)

---

### CPU Baseline Performance

* Execution Time: 1.12 seconds
* IPC: 0.77
* Cycles: ~6.06 billion

The CPU implementation benefits from cache locality due to tiling but is limited by sequential execution and lacks large-scale parallelism.

---

### Baseline GPU Analysis

Initial GPU runs with small workloads showed poor utilization due to insufficient grid size, resulting in only a few SMs being active. Increasing the problem size to 1024×1024 significantly improved utilization, achieving approximately 95% compute and memory throughput. This demonstrated that GPUs require sufficiently large workloads to achieve high efficiency.

---

### Matrix Multiplication Optimization Journey

#### Naive GPU Implementation

Each thread computes one output element using only global memory. This resulted in excessive global memory accesses and no data reuse, leading to poor efficiency.
Execution Time: ~3.47 ms

#### Problem Scaling

Increasing matrix size improved GPU utilization and throughput (~95%), confirming that workload size directly affects performance.

#### Shared Memory Tiling (Most Impactful Optimization)

Shared memory tiles (16×16) were introduced to reduce redundant global memory accesses and enable data reuse across threads.
Execution Time: 2.59 ms
Improvement: ~25% over naive implementation
This optimization significantly reduced memory traffic and improved locality, making it the most effective technique.

#### Block Size Tuning

* 16×16: Best performance
* 32×32: Reduced performance

Larger blocks increased register and shared memory usage, reducing occupancy from ~98% to ~66%. This showed that performance depends on balancing resource usage and parallelism.

#### Bank Conflict Optimization

Shared memory padding (+1) was applied to avoid bank conflicts.

* No improvement in matrix multiplication
* ~35% improvement in transpose kernel

This indicates that bank conflicts are workload-dependent and do not always impact performance.

#### Loop Unrolling

Using `#pragma unroll` did not improve performance and slightly degraded it.
Reason: The kernel is memory-bound, so reducing instruction overhead does not provide benefit.

#### Double Buffering

Two shared memory buffers were used to overlap memory transfer and computation.
No improvement was observed because high occupancy (~98%) already hid memory latency effectively.

#### Vectorized Memory Access (int4)

This optimization degraded performance.
Reason: It broke memory coalescing and introduced irregular access patterns, increasing memory transactions.

---

### Final Matrix Multiplication Performance

* Naive GPU: 3.47 ms
* Tiled (16×16): 2.59 ms (best)
* Double Buffered: 2.67 ms
* Unrolled: 3.75 ms
* Vectorized: 4.02 ms

---

### CPU vs GPU Comparison

* CPU (Tiled): 1.12 sec
* GPU (Best): 2.59 ms
* Speedup: ~432×

The CPU relies on cache optimization, whereas the GPU leverages massive parallelism and efficient memory access.

---

### Memory Coalescing (Critical Concept)

* Coalesced Access: Consecutive threads access consecutive memory locations, resulting in fewer memory transactions and high performance.
* Non-coalesced Access: Strided or irregular access increases memory transactions and reduces performance.

Matrix multiplication was naturally coalesced, while vectorization broke this pattern, causing slowdown. Memory access pattern was identified as the most critical factor in performance.

---

### Reduction Optimization Journey

#### Naive Reduction

Used global memory and frequent synchronization.
Execution Time: ~8 µs (slowest)

#### Shared Memory Reduction

Reduced global memory traffic using shared memory.
Execution Time: ~3.58 µs

#### Warp-Level Reduction

Used `__shfl_down_sync` for register-level communication within a warp, eliminating synchronization overhead.
Initial issue of incorrect results (processing only 256 elements) was fixed using a grid-stride loop:
`for (int i = tid; i < N; i += blockDim.x)`

#### Multi-Block Reduction

Moved from single-block to multi-block execution for full GPU utilization.
Techniques used:

* Grid-stride loop: `idx += blockDim.x * gridDim.x`
* Hierarchical reduction: thread → warp → block → grid

Results:

* Improved utilization
* Memory throughput ~70%
* Occupancy ~82%

---

### Warp-Level Optimization

Warp-level programming eliminates the need for synchronization within a warp since threads are inherently synchronized. This reduces synchronization overhead and improves performance when synchronization is a bottleneck.

---

### Bottleneck Analysis

A key outcome was the ability to classify kernels based on bottlenecks:

* Matrix Multiplication: Balanced (compute + memory)
* Reduction: Memory-bound
* Transpose: Memory-bound

Optimization effectiveness depends on targeting the correct bottleneck:

* Compute-bound: benefit from unrolling and instruction optimization
* Memory-bound: benefit from coalescing, tiling, and memory hierarchy usage

Core Optimizations
1️⃣ Tiling (Shared Memory)

👉 Used to reduce global memory access by reusing data loaded into fast shared memory.

2️⃣ Memory Coalescing

👉 Used to ensure adjacent threads access adjacent memory so GPU can combine accesses into fewer transactions.

3️⃣ Block Size Tuning

👉 Used to balance resource usage (registers/shared memory) and maximize occupancy.

4️⃣ Occupancy Optimization

👉 Used to keep more warps active so GPU can hide memory latency effectively.

5️⃣ Bank Conflict Avoidance

👉 Used to prevent multiple threads accessing the same shared memory bank causing serialization.

🔹 Performance Tweaks
6️⃣ Loop Unrolling

👉 Used to reduce loop overhead and increase instruction-level parallelism (useful for compute-bound kernels).

7️⃣ Double Buffering

👉 Used to overlap memory loads with computation to hide memory latency.

8️⃣ Vectorized Memory Access

👉 Used to load multiple data elements per thread to improve memory bandwidth utilization.

🔹 Warp-Level Optimization
9️⃣ Warp Shuffle (__shfl_sync)

👉 Used to enable direct register-level communication within a warp, eliminating synchronization overhead.

🔟 Warp-Level Reduction

👉 Used to perform reductions efficiently without shared memory or block-wide synchronization.

🔹 Parallel Scaling
1️⃣1️⃣ Grid-Stride Loop

👉 Used to allow fewer threads to process large datasets efficiently by iterating over data in strides.

1️⃣2️⃣ Multi-Block Reduction

👉 Used to distribute work across multiple SMs for full GPU utilization.

1️⃣3️⃣ Hierarchical Reduction

👉 Used to combine results in stages (thread → warp → block → grid) for scalable performance.

🔹 Memory & Execution Insights
1️⃣4️⃣ Global vs Shared Memory Usage

👉 Used to decide where data should reside based on access speed and reuse.

1️⃣5️⃣ Latency Hiding via Occupancy

👉 Used to switch between warps so memory delays don’t stall execution.

🔹 Analysis & Understanding
1️⃣6️⃣ Bottleneck Identification

👉 Used to determine whether kernel is memory-bound or compute-bound to apply correct optimization.

1️⃣7️⃣ Profiling with Nsight Compute

👉 Used to measure performance metrics and guide optimization decisions.

🔹 Bonus Concepts You Practically Saw
1️⃣8️⃣ Workload Scaling

👉 Used to ensure GPU is sufficiently loaded to reflect real performance.

1️⃣9️⃣ Thread-to-Data Mapping

👉 Used to assign work efficiently so all data is processed without redundancy or gaps.

# Note

👉 Reduce memory traffic → Tiling, Coalescing
👉 Reduce idle time → Occupancy, Warp-level, Double buffering
👉 Scale workload → Multi-block, Grid-stride
