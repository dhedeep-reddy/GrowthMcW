# Program 5 — Parallel Reduction (Vector Sum)

I implemented a parallel reduction program to compute the sum of a vector using CUDA. Reduction is a common parallel algorithm where many values are combined into a single result.

The operation performed in the program was the summation of all vector elements.

```
sum = A[0] + A[1] + A[2] + ... + A[N-1]
```

Instead of computing the sum sequentially, I implemented a tree-based reduction where threads cooperate to combine elements in shared memory.

Inside the kernel I used shared memory to store intermediate values.

```
__shared__ int sdata[256];
```

Each thread loaded one element from global memory into shared memory. After loading the data, I used thread synchronization to ensure that all threads completed the memory load before the reduction started.

```
__syncthreads()
```

The reduction was then performed iteratively where half of the threads combined values from the other half of the threads.

```
for(int s = blockDim.x / 2; s > 0; s >>= 1)
```

During each iteration, active threads added the value from a neighboring element in shared memory. This continued until a single value remained. Thread `0` stored the final result in global memory.

Through this program I practiced using shared memory, thread synchronization, and cooperative computation between threads within a block.

# Program 6 — Matrix Multiplication (Naive Implementation)

Next, I implemented matrix multiplication using CUDA. Matrix multiplication is an important operation used in many computational workloads such as machine learning and scientific computing.

The operation computed was:

```
C[i][j] = Σ (A[i][k] * B[k][j])
```

To implement this on the GPU, I assigned each thread the responsibility of computing one element of the output matrix.

I used two-dimensional thread indexing to map threads to matrix coordinates. The thread position was computed using:

```
row = blockIdx.y * blockDim.y + threadIdx.y
col = blockIdx.x * blockDim.x + threadIdx.x
```

Each thread computed the dot product between one row of matrix A and one column of matrix B using a loop over the shared dimension.

In this implementation all memory accesses were performed directly from global memory. This version helped me understand how threads map to matrix elements and how 2D grids and blocks are used for matrix operations. However, this implementation does not reuse memory efficiently and therefore is not optimized.

# Program 7 — Matrix Multiplication using Shared Memory (Tiled Implementation)

After implementing the naive version of matrix multiplication, I implemented an optimized version using shared memory tiling.

In this implementation I divided the matrices into smaller tiles so that threads within a block could reuse values loaded from global memory. I declared shared memory tiles inside the kernel:

```
__shared__ int tileA[TILE_SIZE][TILE_SIZE];
__shared__ int tileB[TILE_SIZE][TILE_SIZE];
```

Each thread loaded one element from matrix A and matrix B into shared memory. After loading the tiles, I used thread synchronization to ensure all threads completed the memory load before computation started.

```
__syncthreads()
```

The computation then used the shared memory tiles to perform partial multiplications. Since the tile values are reused by multiple threads, this reduces the number of global memory accesses and improves performance.

This tiled matrix multiplication approach is widely used in optimized GPU libraries and high-performance computing applications.

Through this implementation I studied how shared memory can be used to improve memory reuse and how tiling techniques help improve GPU performance.

# CUDA Kernel Profiling using Nsight Compute

After implementing the tiled matrix multiplication kernel, I performed GPU profiling using NVIDIA Nsight Compute to analyze how the kernel utilized GPU resources.

I first compiled the program with line information to enable detailed profiling.

```
nvcc -lineinfo matrixMulTil.cu -o matrixMulTil
```

I then ran the profiler using:

```
ncu ./matrixMulTil
```

I also executed a detailed profiling run using:

```
ncu --set full ./matrixMulTil
```

The profiler produced several performance metrics related to compute utilization, memory throughput, occupancy, and warp execution behavior.

---

# Profiling Observations

From the profiler output I observed that the GPU resources were not fully utilized. The kernel launch configuration showed that the grid size contained only one block.

```
Grid Size = 1
Block Size = 256 threads
```

Since the GPU contains 26 streaming multiprocessors, launching only one block means that only one SM executed the kernel while the remaining SMs remained idle.

The profiler reported a warning indicating that the kernel grid was too small to fully utilize the GPU hardware resources.

The compute throughput reported by the profiler was approximately 0.34%, indicating that only a very small fraction of the GPU compute capability was used during the kernel execution.

Memory throughput was also low at approximately 2%, which indicates that the memory subsystem was mostly idle during execution.

The kernel execution time was approximately:

```
3 microseconds
```

This short runtime occurred because the matrix size used for testing was very small.

```
Matrix size = 4 × 4
```

A workload of this size is not sufficient to fully utilize the parallel processing capability of the GPU.

---

# Occupancy Analysis

The profiler reported that the theoretical occupancy of the kernel was 100%. However, the achieved occupancy was approximately 17%.

This difference occurred because the grid size was very small and did not generate enough active warps to keep the GPU schedulers fully occupied.

Low occupancy is expected when the workload is extremely small relative to the GPU hardware capacity.

---

# Warp Execution Behavior

The profiler also reported that the average number of active threads per warp was approximately 31.69. Since a warp consists of 32 threads, this indicates that almost all threads were active during execution.

This observation indicates that the kernel does not suffer from warp divergence.

Some warp stall cycles were observed due to synchronization barriers caused by the `__syncthreads()` instruction, which is expected in tiled matrix multiplication kernels where threads must synchronize after loading shared memory tiles.
