Today I worked on optimizing and analyzing a large matrix transpose implementation in C++ with a strong focus on performance measurement, memory behavior, multi-core scaling, and validation methodology.

I began with a basic matrix transpose implementation and modified it to use a very large matrix size of 8192 × 8192 in order to make profiling meaningful. Using double precision, the total memory footprint for two matrices was approximately 1 GB. The code was compiled with -O3, -march=native, and -g to allow optimization and profiling with perf.

Running perf stat -d on the naive transpose showed low IPC (around 0.63) and a very high L1 data cache miss rate of approximately 52 percent. Stalled cycles per instruction were high, confirming that the kernel was memory-bound. The assembly output from perf annotate confirmed that the compiler had vectorized the inner loop using AVX instructions such as vmovupd, meaning the bottleneck was not lack of vectorization but poor memory access patterns. The strided write pattern B[j * N + i] caused large memory jumps (64 KB stride), leading to cache thrashing and high miss rates.

Next, I implemented a blocked (tiled) transpose with a block size of 64. This improved cache locality by operating on smaller submatrices. After profiling, runtime reduced from about 0.58 seconds to around 0.35 seconds in single-threaded execution. IPC increased and the L1 miss rate dropped to around 28 percent. This demonstrated the impact of spatial locality and cache-aware blocking.

I then parallelized the blocked version using OpenMP. Initially, I forgot to compile with -fopenmp, and perf showed that only one CPU was utilized. After recompiling correctly and running with different thread counts using OMP_NUM_THREADS, I measured scaling at 1, 2, 4, 8, 16, 24, and 32 threads. The results showed near-linear scaling up to about 8 threads, with diminishing returns afterward. The best runtime achieved was approximately 0.115 seconds. Speedup plateaued around 4.8× relative to single-threaded blocked execution. perf reported over 20 CPUs utilized, but IPC per core dropped significantly under high thread counts. This behavior confirmed that the kernel became limited by memory bandwidth. Hyperthreading did not provide additional performance improvement.

After analyzing memory bandwidth limitations, I experimented with reducing data size by switching from double (8 bytes) to float (4 bytes). Since transpose performs no arithmetic operations, precision was not a concern for this kernel. The float version reduced total memory traffic by half. Running the same blocked + OpenMP version with float reduced the best runtime further to approximately 0.069 seconds. The speedup relative to the double version was about 1.66×. This confirmed that performance scaled with bytes moved and that the workload was bandwidth-bound. Estimated sustained bandwidth from the float case was consistent with earlier observations.

Following performance experimentation, I raised the issue of validation. With multiple optimizations applied (blocking, parallelization, data type changes), it became necessary to verify that optimized output matched the reference implementation. I discussed the importance of maintaining a simple reference implementation and comparing outputs using a tolerance-based validation function for floating-point values. This avoids silent correctness issues when reordering operations or parallelizing code.

I then moved to formal benchmarking methodology using Google Benchmark, similar to what was done in the Performance Ninja playlist. I installed libbenchmark-dev and created a structured benchmarking setup including:

* A reference transpose implementation.
* An optimized (blocked + OpenMP) implementation.
* A validation step executed before benchmarking.
* Separate benchmark functions for reference and optimized versions.
* Use of benchmark::ClobberMemory to prevent compiler optimizations.

The final structure included initialization, validation, and benchmark execution inside main. This allowed automated timing, multiple iterations, and statistically stable results instead of relying on single chrono measurements.
